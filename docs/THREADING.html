Threads in documents-analyst, by example

Two folders of contracts are waiting, each is processed on its own thread, a human approves one change, and the register updates. Here is what each thread does, what the threads share and how that is made safe, why files inside one folder still go strictly one at a time — and why the threads it doesn’t have are the more interesting decision.

The setup

Every subfolder of the watched folder is one pile, with its own run, review queue, history and final-document.docx. Piles are never compared with each other, which is what lets them run side by side. The worker process has four kinds of thread:

ThreadWhat it may doWhat it may never do
main Discover piles and ingest them — scan, hash, parse — one pile after another, and check each final document; then submit a graph drain if none is running, and wait for the next tick Block forever, or wait for graph work. Every wait has a timeout
graph-drain One executor thread, one drain at a time: resume reviewed piles, then run ready ones, fanning out to the lanes Hold up discovery. A slow LLM call never delays another pile’s scan or repair
pile lanes pile_0… Up to pile_concurrency of them (default 3). Each claims one pile, runs or resumes its graph, writes its final document, then claims the next Take a pile another lane, thread or container holds. Run two files of one pile at once
notify-listener Set one boolean: wake Touch the database, carry a pile id, do any work

The main thread and the listener share two booleans — wake (“look sooner”) and stopped (“shut down”) — and nothing else. A wake that lands while a drain is still running is remembered (missed), and the drain’s done-callback sets wake when it finishes, so an approval does not wait out the rest of the 30 seconds. The lanes also read stopped before claiming another pile, and they share the graph environment that was opened once per process; the section after the example says what is in it and how each part is made safe. pile_concurrency: 1 restores strictly one pile after another, still on the drain thread.

Two folders at once: one lane per pile

folder1 holds 5 files and folder2 holds 10. Discovery reads both on the main thread; then the graph-drain thread fans out to the lanes while the main thread goes back to its timer. Each lane claims a pile with FOR UPDATE SKIP LOCKED plus a fenced lease in one statement (queue.claim_and_lease), so a row one lane has locked is simply skipped by the next — folder2 does not wait for folder1’s extraction, and the third lane finds nothing and returns.

Lane owner ids are <worker_id>/lane-N when there is more than one lane, so lease_owner_id says which thread holds a pile. That is for reading only: fencing is by lease epoch, never by owner. Reviewed piles are resumed in parallel the same way, under the same lane cap. A lane or pile that raises is logged and costs only itself; the other piles carry on.

Inside one pile: strictly one file at a time

The lanes parallelise piles, never files. A pile’s graph is

Resolve → Ingest → Extract → Match → Classify → Audit → HumanGate → Commit → Reconcile → Audit (pass 2)

Ingest and Extract each loop over the pile’s documents one at a time, in discovery order (ORDER BY created_at). File 1 is fully extracted before file 2 starts; no two files of one pile are ever in flight at once. Then the cross-file stages — matching facts across files, conflicts and amendments, the rulebook audit, human review, and the final-document write — run once over the whole pile.

It is not “finish file 1, including the final document, before file 2”. A conflict needs two files to exist, so the document is written once per review round, not once per file. A file added later goes through the same steps, and only the sections it affects change.

The example, moment by moment

Zoom in on one pile. You copy three contracts into acme/ in the watched folder (watched/ by default, or your WATCH_DIR) at the instant the worker boots. Here is the real sequence. The graph work runs on a pile lane under the graph-drain thread; the timeline folds both into the main column, because with one pile nothing else is happening on the main thread.

Four moments worth pausing on

0.01 s — the listener sets wake the moment it connects. Not because anything happened, but because anything published while it was connecting is gone forever. Waking once on connect turns that hole into one early scan.

0.40 s — the first 30-second wait returns instantly. The flag was already set, so wake.wait(30) returns True straight away. This is the whole mechanism: the wait is not a sleep, it is a sleep that can be interrupted.

30.7 s — the files were skipped twice on purpose. A file younger than SETTLE_SECONDS might still be copying. Hashing a half-written PDF records a document that never existed. Skipping is free; the next pass is 30 seconds away.

~240 s — the pause costs zero threads. This is the part people expect to be wrong. The run stops at the human gate, writes a LangGraph checkpoint to Postgres, releases the lease, and the lane goes straight on to claim the next pile — with two folders waiting, it would pick up the other one in the same pass. Nothing is blocked. The person can take three days, the machine can reboot fifty times, and the run is still exactly where it was.

A naive design would park a thread here — some worker sitting in approval_event.wait() holding a database connection and a lease. That thread dies with the process, so a restart would lose the pause. Here the pause is a row, so it outlives everything.

What the lanes share, and how each part is made safe

The graph environment is opened once per process — loading gigabytes of weights per thread, or per tick, would spend the interval on setup — so every lane uses the same objects. Here is what happens when two piles reach each one at the same moment.

SharedThe riskHow it is made safe
checkpointer Two lanes writing LangGraph checkpoints through one PostgresSaver Already locks per cursor, so it is thread-safe as it stands
LLM clients (extraction, judge) One pile’s request leaking into another’s Stateless per call; nothing survives from one request to the next
embeddings last_usage overwritten by the other pile, so a cost report shows a neighbour’s tokens last_usage is thread-local: each pile’s cost report gets its own embedding usage
NLI and NER models Hugging Face fast tokenizers are not thread-safe — two threads in one raise “Already borrowed” models.shared_across_threads wraps DeBERTa and GLiNER in _Serialized, a per-model lock. Calls take milliseconds next to an LLM call’s seconds, so taking turns costs nothing visible
a pile Two lanes running the same pile FOR UPDATE SKIP LOCKED plus a fenced lease; every write carries the lease epoch
The LLM calls are the part that runs concurrently — that is the point. It also means raising pile_concurrency multiplies the request rate against your provider. Raise it only as far as the provider’s rate limit allows; 1 puts the piles back in a queue.

Why there is no heartbeat thread

The lease has a 90-second TTL, so something has to keep renewing it during a long run. The obvious answer is a background thread ticking every 30 seconds. documents-analyst renews it inline instead — before each document in ingest.py, and before each bounded unit of graph work (an embedding batch, a model request) through renew_lease in graph/context.py. Each lane renews only its own pile’s lease, so this is unchanged by running several piles at once.

Here is why, and it is the sharpest threading decision in the project.

The code says it in one sentence:

def renew_lease(self, fence: Fence) -> None:
    """Give the next bounded unit of graph work a full lease TTL. Called at
    work boundaries, not from a background thread — a background renewer could
    keep authority alive while a model call is stuck, where renewing before a
    bounded operation lets a genuinely stalled worker be taken over."""

The general rule, worth stealing: a liveness signal should be a by-product of progress, not a separate thing that runs on a timer. The moment they are separate, the signal can keep firing after the progress stops.

What breaks if you remove each piece

RemoveWhat happensSeverity
the listener thread Approvals take up to 30 s to be noticed instead of ~1 s. Everything still works latency only
wake.clear() before the pass A notification arriving during a pass is cleared afterwards and lost. The pile waits a full tick a real bug
the timeout=1.0 on notifies() On a quiet system the listener never checks stopped, so it blocks shutdown a real bug
the settle check Half-copied PDFs get hashed and stored as documents that never existed corrupt data
the missed wake An approval that lands during a drain waits out the rest of the 30-second tick latency only
the separate drain thread Discovery and final-document repair stall behind a slow LLM call in any pile latency only
the per-model lock Two piles reach the NLI or NER tokenizer together and one run fails with “Already borrowed” a real bug
thread-local last_usage One pile’s cost report records another pile’s embedding tokens wrong numbers
the lanes (pile_concurrency: 1) Folder 2 waits for folder 1’s extraction. Everything still works throughput only
epoch fencing A frozen worker wakes after losing its lease and keeps writing over the new owner silent corruption

Notice the shape: losing a thread — the listener or the extra lanes — costs latency or throughput. Losing any of the database mechanisms, or the locks around what the lanes share, costs correctness. That is the division the whole design is built on.
